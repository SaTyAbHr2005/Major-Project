# Module 5: Automated Preprocessing Engine

## Overview

Module 5 is the Automated Preprocessing Engine. It consumes the dataset and DatasetProfile generated by Module 4 and prepares data for the downstream ML pipeline without modifying the original source files.

The module provides scalable output modes, quality validation, quarantine tracking, leakage-safe transformations, deterministic splitting, class-balancing support, manifests, reporting, and a CLI.

Module 5 does not perform model training, Federated Learning (FL), or Differential Privacy (DP).

## 1. Objectives

Module 5 is responsible for:

- Consuming the Module 4 dataset and profile.
- Discovering and validating input samples.
- Detecting invalid image and tabular data.
- Recording rejected samples without deleting source files.
- Creating reproducible train/validation/test splits.
- Preventing preprocessing data leakage.
- Supporting patient/group-aware splitting.
- Handling training-set class imbalance.
- Supporting lazy and materialized output modes.
- Producing manifests, metadata, and reconciliation reports.
- Providing a repeatable command-line interface.
- Providing automated tests for normal and edge-case behavior.

## 4. Configuration

config.py provides dataclass-based configuration for:
- output mode
- split strategy
- split proportions
- random seed
- grouping column
- image validation rules
- tabular validation rules
- imputation
- encoding and scaling
- class balancing
- storage safety
- output locations

The two primary output modes are:
- lazy
- materialized

## 5. Dataset Discovery

The engine performs incremental discovery of image files using os.walk rather than loading an entire dataset into memory.

This supports large datasets by avoiding unnecessary RAM usage during discovery and quality assessment.

The discovery process tracks source paths, labels, sample counts, and estimated storage requirements.

## 6. Image Quality Validation

image/quality.py uses Pillow and NumPy for dependency-light validation.

Checks include:
- Corruption: Unreadable or malformed image files can be rejected.
- Zero-byte files: Files containing zero bytes are treated as invalid.
- Brightness: Configured brightness boundaries can identify extremely dark or bright samples.
- Blur: Laplacian variance is used as a blur-related quality signal.

The original source images are not modified by these checks.

## 7. Tabular Quality Validation

tabular/quality.py evaluates tabular data before transformation.

It supports:
- severe missingness detection
- configurable missingness limits
- IQR-based outlier detection

The validation stage identifies problematic data without destructively modifying the source dataset.

## 8. Quarantine Management

quarantine/manager.py provides non-destructive rejection tracking.

```text
Invalid sample
     │
     ├── source remains unchanged
     │
     └── rejection reason → quarantine registry
```

Rejected samples are not deleted. Their failure reasons are recorded so preprocessing decisions remain traceable.

## 9. Label Hierarchy

labels/hierarchy.py provides label mapping functionality required by the preprocessing pipeline.

Labels are mapped into the representation required for downstream processing while maintaining their relationship with the original samples.

## 10. Dataset Splitting

splitter.py provides deterministic splitting using configurable random seeds.

- Stratified splitting: StratifiedShuffleSplit is used where appropriate to preserve class distributions.
- Fallback: If stratification is mathematically impossible, the splitter can fall back to random splitting instead of unnecessarily failing the complete preprocessing operation.
- Grouped splitting: GroupShuffleSplit is supported when a grouping identifier such as Patient ID is available. This prevents samples belonging to the same group from being distributed across incompatible dataset boundaries.

## 11. Class Balancing

balancing/sampler.py supports training-oriented class balancing strategies including:
- class weights
- oversampling
- undersampling

Balancing decisions are based on the training split only. Validation and test distributions are not modified for balancing purposes.

## 12. Tabular Preprocessing and Leakage Prevention

The tabular preprocessing components are:
```text
tabular/
├── missing_values.py
└── encoding.py
```

Preprocessing parameters are fitted exclusively on the training data.

```text
Training
   │
   ▼
FIT parameters
   │
   ├── Imputation
   ├── Encoding
   └── Scaling
   │
   ▼
Frozen metadata
   │
   ├──────────────┐
   ▼              ▼
Validation       Test
TRANSFORM        TRANSFORM
```

Supported behavior includes:
- mean imputation
- median imputation
- mode imputation
- constant imputation where configured
- categorical encoding
- standard scaling
- min-max scaling

Validation and test data do not participate in fitting.

## 13. Image Transformations

image/transforms.py handles deterministic base operations such as:
- resizing
- image format normalization
- RGBA-to-RGB conversion

These operations can be materialized where configured.

## 14. Training Augmentation Separation

image/augmentation.py keeps random training augmentation separate from deterministic preprocessing.

Random augmentations are not permanently baked into the dataset by Module 5. Instead, augmentation rules are retained as metadata for Module 7.

```text
Module 5
  │
  ├── deterministic transforms → may be materialized
  │
  └── random augmentation rules → metadata
                                      │
                                      ▼
                                   Module 7
                                      │
                                      ▼
                              PyTorch DataLoader
```

This allows random augmentation to occur dynamically during training.

## 15. Lazy Output Mode

Lazy mode avoids unnecessary physical duplication of large datasets.

Example:
```bash
python -m hospital_client.preprocessing preprocess \
    /path/to/dataset \
    --profile /path/to/dataset_profile.json \
    --output /path/to/output_dir \
    --mode lazy
```

Typical manifests are:
- train_manifest.json
- validation_manifest.json
- test_manifest.json

They provide lightweight references to source files together with labels, split information, and relevant transformation metadata.

The original files remain in their source location. Lazy mode is particularly suitable when datasets are large or physical duplication is undesirable.

## 16. Materialized Output Mode

Materialized mode physically generates processed output.

A typical structure is:
```text
output/
├── train/
├── validation/
├── test/
├── train.csv
├── validation.csv
├── test.csv
└── manifests / metadata
```

The exact output depends on dataset type and configuration.

## 17. Materialized Storage Safety

output/materializer.py uses psutil to check available disk space before large materialization operations.

A configurable safety buffer is applied.

Conceptually:
```text
Estimated output requirement
          +
Configured safety buffer
          ↓
Available disk space
```

If the available storage does not satisfy the configured requirement, materialization is stopped rather than risking disk exhaustion.

## 18. Manifests and Metadata

output/manifest_builder.py generates lightweight indexes connecting the source dataset with downstream processing.

Manifest information can include:
- source path
- label
- split assignment
- transformation metadata
- augmentation metadata
- downstream-required information

This prevents Module 7 from having to rediscover the dataset.

## 19. Reporting and Reconciliation

reporting/report_generator.py generates human-readable and machine-readable reports:
- preprocessing_report.md
- preprocessing_report.json

Reports provide information about:
- discovered samples
- accepted samples
- rejected samples
- split counts
- preprocessing decisions
- output information
- metadata

The core reconciliation requirement is:
discovered_samples = accepted_samples + rejected_samples + review_samples (when a review state is used).

The purpose is to prevent silent sample loss.

## 20. Command-Line Interface

The CLI is exposed through:
- __main__.py
- cli.py

General usage:
```bash
python -m hospital_client.preprocessing preprocess \
    <dataset_path> \
    --profile <profile_path> \
    --output <output_dir> \
    --mode <lazy|materialized>
```

Example:
```bash
python -m hospital_client.preprocessing preprocess \
    ./data \
    --profile ./data/dataset_profile.json \
    --output ./processed \
    --mode lazy
```

## 21. Data Safety and Immutability

Module 5 follows a non-destructive processing principle.

The source dataset is treated as read-only.

Module 5 must not:
- delete source samples
- overwrite source images
- modify source tabular files
- silently discard rejected samples

Instead:
```text
Original Dataset
      │
      ├── read
      │
      └── process → separate output
```

Rejected samples are tracked through quarantine.

## 22. Module 4 Boundary

Module 4 is the upstream source of the dataset profile and detected dataset information.

Module 5 consumes that information and performs preprocessing without replacing or modifying the Module 4 implementation.

The Module 4 source dataset remains the upstream input boundary.

## 23. Contract with Module 7

Module 5 is the final preparation stage before ML training.

Module 5 explicitly does not perform:
- model training
- Federated Learning (FL)
- Differential Privacy (DP)

### Materialized mode
Module 7 receives:
- processed train dataset
- processed validation dataset
- processed test dataset
- transformation metadata
- manifest/output metadata

### Lazy mode
Module 7 receives:
- train_manifest.json
- validation_manifest.json
- test_manifest.json
- transformation metadata
- augmentation metadata
- raw source paths

In lazy mode, Module 7 can use the manifests to locate source files and apply required runtime processing. Random training augmentation is applied dynamically by the downstream training pipeline.
